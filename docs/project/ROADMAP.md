# 改造路线

更新：2026-09-30。状态：建议路线，具体实现按阶段细化。本文件不承载实时进度，见 [PROGRESS.md](PROGRESS.md)。

## 推荐顺序

| 阶段 | 产出 | 退出条件 |
| --- | --- | --- |
| M0 基线与适配可行性 | 固定上游提交、可重复的 Windows 构建记录、鸿蒙平台依赖清单和最小桥接验证 | Windows 原版运行；鸿蒙原生调用可在目标设备执行；连接/媒体适配的可行项与阻塞项有证据 |
| M1 鸿蒙最小远控 | ArkUI 连接页和会话页，通过自建服务连接 Windows | ID/授权、中继、可达 IP 直连、视频、基础键鼠、断开回收在真机验收；自动打洞单独记录 |
| M2 交互体验 | 触控板/直接触控、右键拖拽、缩放、键盘及前后台恢复 | 固定手机/平板用例通过；主观体验结合真实操作反馈评估 |
| M3 Windows 省流 | 基线测量与有实测收益的采集/编码/发送改动 | 静止、打字、鼠标、滚动、视频五类场景有前后数据；保留协议兼容与首帧/重连正确性 |
| M4 应用窗口模式 | Windows 应用选择、窗口采集、输入范围控制 | 弹窗、失焦、关闭、最小化行为明确；桌面模式不回归；隔离能力不夸大 |
| M5 平台与协议扩展 | macOS 被控、Android/iOS 控制、按需求接入其他协议 | 每次只扩展一个目标并建立对应平台/协议验收矩阵 |

自动打洞若在 M1 未通过，就只能标为尚未支持，不能用中继成功替代直连成功。产品是否接受中继优先的早期版本，在 M1 结果后决定。

## 为什么这样排序

1. 推荐：先验证官方基线与鸿蒙适配，再优化交互和 Windows 画面。最先暴露原生库、SDK 和设备权限风险。
2. 先改 Windows 省流：容易用官方控制端比较数据，但无法验证首发鸿蒙端，适合以后单独开展。
3. 同时重写多协议与多端：并行面过大，难以定位连接、平台和体验问题，不作为当前路线。

## 已定位的代码入口

这些是调查入口，不是要求立即重构所有模块；以仓库 AGENTS.md 的最小改动原则为准。

| 目的 | 入口 | 备注 |
| --- | --- | --- |
| 鸿蒙编译与平台依赖 | `Cargo.toml`、`src/lib.rs`、`src/platform/` | 当前移动平台条件大量针对 Android/iOS，不能简单增加目标名称就算移植完成 |
| 客户端会话与 UI 边界 | `src/client.rs`、`src/ui_session_interface.rs`、`src/flutter.rs`、`src/flutter_ffi.rs` | 官方代码已有会话/UI 结构，但包含具体平台和桥接依赖 |
| 被控端视频与编码调度 | `src/server/video_service.rs`、`src/server/video_qos.rs` | 先阅读已有无新帧分支和编码器行为，再做测量 |
| 屏幕采集与编解码 | `libs/scrap/` | 按 Windows/macOS 实际后端调查；不要泛化某个后端的差分能力 |
| 被控端输入 | `libs/enigo/`、`src/server/input_service.rs` | 与连接权限一起评估，应用模式需额外处理焦点 |
| 共享协议和配置 | `libs/base/`、`libs/hbb_common/` | 后者是官方子模块，优先避免无必要变更 |

## Git 与阶段交付

- `origin` 当前是用户 fork；官方 `upstream` 尚未配置。
- `master` 保留基线，功能使用独立分支；集成分支规则在开始首个代码阶段时确定。
- 当前文档放在 `docs/project/`。未来独立鸿蒙仓库建立后，再确定共享核心版本引用；不先复制一套核心长期分叉。
- 每阶段只在相关路径改动，记录默认路径与平台回归范围。

第一阶段规格：[001-baseline-and-harmony-feasibility.md](specs/001-baseline-and-harmony-feasibility.md)。

## Windows 省流调查结论（基线 a7f226020）

- `libs/scrap/src/dxgi/mod.rs:600` 已使用画面更新时间/累计帧信息判定新帧；`libs/scrap/src/common/mod.rs:122` 有相等帧过滤。具体行为取决于采集后端。
- `src/server/video_service.rs:911` 对非零延迟编码器保留有限次数重复编码旧 YUV 的路径；不能贸然删掉，也不能承诺静止立刻零视频流量。
- `src/server/video_qos.rs` 已管理帧率与码率；`src/server.rs:150`、`src/server/input_service.rs:356` 已有独立光标服务。首先确认目标路径是否使用这些能力。
- 当前检查到的主发送路径为视频编码后发送；没有证据表明已实现自定义 dirty-rectangle 图块传输。视频帧间预测与图块传输需要区分。
- `src/server/video_service.rs:584` 的视频源分派为显示器或摄像头，应用窗口模式需要独立评估新增路径。
