# 产品 SPEC

更新：2026-09-30。状态：需求整理草案，按已讨论方向记录；性能目标和首发范围仍需通过第一阶段验证收敛。

## 产品目标

提供类似 ToDesk 的设备连接与远程协助流程，优先改善鸿蒙手机/平板操作 Windows 当前桌面的体验。以用户 fork 的 RustDesk 官方代码为主线，复用成熟连接与协议能力，在实测基础上优化带宽和画面输出。

## 架构方向

- Windows 被控端基于本 fork 改造，首阶段保持 RustDesk 协议及原有路径。
- 鸿蒙控制端优先 ArkTS/ArkUI，原生媒体和系统能力通过鸿蒙适配层接入。
- 复用官方 Rust 会话与连接能力是优先方向，不意味着官方核心已是可直接移植的独立 SDK。跨编译依赖、平台条件编译和界面边界必须先验证。
- 后续多协议能力位于控制端；各协议通过能力声明驱动界面，不要求被控端同时提供全部协议。
- Android/iOS 是否直接沿用官方 Flutter 界面，随扩展阶段决定。当前不承诺全部平台共用一套 UI。
- RemoteDeskHarmonyOS 仅作适配参考，不作为主开发基线，也不直接继承其验证结论。

## 许可与安全边界

被控端接受基于 AGPL 代码改造的方向。控制端是否必须闭源尚无最终决定：若复用或组合 RustDesk 的 AGPL 实现，应按适用义务规划，不得预设只公开被控端就足够。

若控制端闭源成为硬约束，需要重新确认独立实现或其他授权路线，再决定引入哪些代码。运行时密钥、用户数据和授权记录不进入源码仓库。保留现有认证、身份验证和权限路径，涉及变更时单独评审。

## 成功判据

- 鸿蒙真机可以连接 Windows 当前会话，画面和触控位置一致，授权拒绝有效。
- 可以区分 IP 直连、NAT 穿透直连与中继，且分别提供测试证据。
- 省流改动与固定版本上游在同条件下比较流量、CPU、帧率、文字清晰度和输入反馈；未建立基线前不制定没有依据的节省百分比。
- 应用模式不会把“只采集窗口”宣传为安全隔离；失焦和独立弹窗有明确处理。
- 文档中的完成状态可以追溯到实际验证结果。
